# STEP 7. Open-source LLM vs Cloud API 비교

## 실험 조건

공통 세트는 `set01` ~ `set05` 다섯 개다. 프롬프트와 명부는 세 모델 모두 같은 것을 받는다.

| 구분 | 모델 | 반복 | 호출 수 |
|---|---|---|---|
| Local | `qwen3:4b-instruct-2507-q4_K_M` | 세트당 2회 | 10 |
| Local | `gemma3:4b` | 세트당 2회 | 10 |
| Cloud | `gpt-5.6-luna` | 세트당 1회 | 5 |

**반복 수가 다르다.** Local은 2회를 모두 넣어 평균을 냈고, 좋은 결과 한 건만 골라 쓰지 않았다.
Cloud는 1회뿐이라 회차 간 변동을 알 수 없다.

생성 설정은 `temperature` 0으로 맞췄다. Local은 `num_ctx` 16384, Cloud는 해당 항목이 없다.
출력 한도는 양쪽 모두 지정하지 않았다.

## 실측 결과

### Quality

| | qwen3 (n=10) | gemma3 (n=10) | gpt-5.6-luna (n=5) |
|---|---|---|---|
| 호출 성공 | 10/10 | 10/10 | 5/5 |
| 정답 포함 | 4.1 / 10 | 2.3 / 10 | **8.0 / 10** |
| 제외 대상 혼입 | 1.3 | 0.9 | **0.0** |
| 형식 미달 | 8회 | 7회 | 1회 |

통과선은 포함 7명 이상, 제외 혼입 0이다. **Cloud만 통과하고 Local 둘은 미달이다.**

Cloud 세트별 내역이다.

| 세트 | 포함 | 제외 혼입 | 시간 | 입력 토큰 | 출력 토큰 | 형식 |
|---|---|---|---|---|---|---|
| set01 | 9/10 | 0 | 16.3초 | 9,451 | 1,419 | OK |
| set02 | 8/10 | 0 | 19.3초 | 9,293 | 1,730 | OK |
| set03 | 7/10 | 0 | 11.5초 | 9,147 | 925 | OK |
| set04 | 8/10 | 0 | 9.0초 | 8,982 | 848 | 명부에 없는 id `임서영` |
| set05 | 8/10 | 0 | 10.8초 | 9,436 | 913 | OK |

set04의 형식 미달은 `id` 자리에 식별값 대신 이름을 넣은 것이다. 나머지 9명은 정상이었다.

### Latency

| | qwen3 | gemma3 | gpt-5.6-luna |
|---|---|---|---|
| 평균 응답 시간 | 12.7초 | 10.0초 | 13.4초 |
| 최소~최대 | — | — | 9.0 ~ 19.3초 |

Cloud 값에는 **네트워크 왕복 시간이 포함**돼 있다. Local은 같은 PC 안에서 도는 시간이다.
두 값은 측정 구간이 달라 같은 척도로 보면 안 된다.

**생성 속도(tokens/s)는 Cloud에서 계산하지 않았다.** 응답에 생성 구간 시간 통계가 없다.
전체 응답 시간으로 나누면 네트워크 지연이 섞이므로 값을 채우지 않고 비워 뒀다.

첫 토큰 지연은 양쪽 모두 측정하지 않았다. 위 시간은 TTFT가 아니다.

### Cost

**Cloud — 추정치.** 공통 5회분이다.

| 항목 | 값 |
|---|---|
| 입력 | 46,309 토큰 |
| 출력 | 5,835 토큰 |
| 단가 | 입력 $0.20 / 출력 $1.20 (1M 토큰당) |
| 추정 비용 | **$0.0163** |

**이 숫자는 토큰 수에 단가를 곱한 추정이며 실제 청구액이 아니다.** 실제 사용 내역은
`platform.openai.com`의 Usage 페이지에서 따로 확인해야 한다.

실제로 보낸 요청은 5회보다 많다. 비교에 쓰지 않은 실행까지 포함하면 아래와 같다.

| 구분 | 호출 | 입력 | 출력 | 추정 |
|---|---|---|---|---|
| 비교에 사용 | 5 | 46,309 | 5,835 | $0.0163 |
| 전체 기록 (워밍업·미사용분 포함) | 21 | 193,857 | 22,105 | $0.0653 |

**Local — 측정하지 않음.** 장비는 이미 보유한 RTX 5060 Laptop이고 추가 지출이 없다.
전력 소비는 측정 장비가 없어 재지 않았다. 호출당 한계비용은 0에 가깝지만, 장비 가격과
전력·관리 비용을 모두 넣으면 호출 수가 적을수록 단가가 불리하다. 이 프로젝트에서는
숫자로 비교하지 않는다.

## 운영 조건 분석

아래는 실측이 아니라 서비스 요구사항에 따른 판단이다. 위 실측 결과와 구분한다.

| 기준 | Local LLM | Cloud API |
|---|---|---|
| Security | 명부가 PC 밖으로 나가지 않는다. 건강·경조사·기도제목을 다루므로 STEP 1의 전제 조건이다 | 외부 API에 원문을 보낸다. 실제 교인 데이터로는 쓸 수 없다 |
| Infrastructure / Operations | 장비 확보와 Ollama 서빙이 필요하다. 모델 교체·업데이트를 직접 관리한다 | 인프라 부담이 낮다. 대신 모델 단종과 요금 변경에 노출된다 |
| Customization | 모델 교체, 양자화 선택, 내부망 구성이 자유롭다 | 제공되는 모델과 API 범위 안에서만 가능하다 |

**이번 실험은 전부 합성 데이터로 수행했다.** 실제 교인 명부는 Cloud로 보내지 않았다.

## 결론

품질만 보면 Cloud가 확실히 낫다. 정답 포함이 8.0 대 4.1·2.3이고 제외 혼입이 0이다.
같은 프롬프트와 같은 명부를 줬으므로 **과제나 프롬프트가 잘못된 것이 아니라 4B 모델의
한계**라는 뜻이다.

그러나 **Cloud는 이 서비스에 쓸 수 없다.** STEP 1에서 로컬 실행을 전제 조건으로 못박았고,
실제 명부에는 건강·경조사·기도제목이 들어 있다. Cloud는 어디까지나 "4B가 못 푼 원인이
모델 크기인지 과제 설계인지" 가리는 대조군이다.

따라서 남는 선택지는 **더 큰 로컬 모델**이다. 응답 시간이 60초 기준에 10~13초이고 VRAM도
8GB 중 2.7~4.9GB만 쓰므로 7~8B급을 올릴 여유가 있다.

## 한계

- Cloud는 세트당 1회뿐이라 **회차 간 변동을 모른다.** Local은 2회를 돌려 같은 명부에 다른
  답이 나오는 것을 확인했는데, Cloud도 그런지는 이 실험으로 알 수 없다.
- Cloud 응답 시간에 네트워크 조건이 섞여 있고, 측정 시점의 네트워크 상태를 따로 기록하지
  않았다.
- 비용은 추정치다. 실제 청구액과 대조하지 않았다.
- 근거 사실성과 한국어 표현은 사람이 읽어야 하는 항목인데 아직 전수 확인하지 않았다.
